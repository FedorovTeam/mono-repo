# usecases

## Загрузка оригинала через подписанную ссылку
1. Клиент добавляет `Authorization: Bearer <jwt>` (issuer `https://auth.tech.fedorov-team.tech/application/o/console/`, audience `L6AmiswYzea2gAs5aGfzhLP9jlapG42ppPhtutoF`; при включённом API‑ключе допускается `X-API-Key`) и при необходимости `X-Correlation-ID`, затем вызывает мутацию `uploadKnowledgeDocument` с параметрами `fileName`, `fileSizeBytes`, `repository`, `branch`, `path` (опционально). Значение `repository` передается как есть (gateway не разбирает владельца и не заполняет `repositoryOwner`).
2. gateway гарантирует наличие `correlation-id`, валидирует обязательные поля (`fileName`, `repository`, `branch`) и положительный `fileSizeBytes`; `path` можно не указывать или передать пустым/пробельным — тогда перед созданием документа gateway подставит путь по умолчанию `knowledge/docs/<documentId>.md`. После валидации запрашивается подписанная PUT‑ссылка через `storage-service.GenerateUploadURL`, TTL берётся из `uploads.signedUrlTtlSeconds`.
3. После генерации ссылки вызывается `document-service.CreateDocument` с новым `document_id`, переданными метаданными, `correlation-id` и bucket/object ключами из ответа хранилища.
4. В ответе GraphQL клиент получает `uploadUrl`, `uploadMethod` (`PUT`), `requiredHeaders` (обязательные для подписи PUT, как минимум `x-amz-meta-correlation-id`) и объект документа со статусом из document-service (обычно `UPLOADED`), `jobId` и прочими метаданными. `correlation-id` дублируется в заголовке ответа.
5. Клиент загружает файл по `uploadUrl` методом `PUT`, обязательно добавляя заголовки из `requiredHeaders`; иначе S3 вернёт ошибку подписи. После события `s3:ObjectCreated:*` MinIO отправляет webhook на `/internal/storage/uploaded`. gateway разбирает каждое уведомление, декодирует `objectKey`, извлекает `document_id` из имени файла (часть до расширения), восстанавливает `correlation-id` из `x-amz-meta-correlation-id` в `userMetadata/responseElements` или генерирует новый, если метаданные пустые, и подтверждает загрузку через `document-service.ConfirmUpload`. Если ни одно уведомление не обработано, HTTP‑ответ — `400 Bad Request`, иначе `202 Accepted`.

## Получение статуса/списка документов
1. С авторизацией по `Authorization: Bearer` (или `X-API-Key`, если разрешён) выполняется запрос `knowledgeDocument(id)` или `knowledgeDocuments(filter, pagination)`.
2. gateway гарантирует `correlation-id`, пробрасывает его, API‑ключ (если есть) и данные пользователя (`x-user-id`, `x-user-email`, `x-user-groups`) в gRPC‑запросы `document-service`, мапит статусы (`UPLOADED/ STORED_ORIGINAL/ CONVERTED_TO_MARKDOWN/ PUBLISHED_TO_GITHUB/ FAILED`) и возвращает найденный документ или список.
3. Пагинация по `limit/offset` (по умолчанию `10/0`), фильтр по статусу и строке `repository` передается в document-service без трансформации.
