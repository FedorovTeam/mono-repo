# flows

## Upload → Convert → Publish
1. Клиент выполняет GraphQL-мутацию `uploadKnowledgeDocument` с обязательными `fileName`, `fileSizeBytes`, целевыми `repository`, `branch` и опциональным `path`, передавая `Authorization: Bearer <jwt>` (или `X-API-Key`, если он включён) и при желании `X-Correlation-ID`.
2. CorrelationID middleware прикладывает `correlation-id` к контексту и ответу; use-case проверяет только заполненность `fileName`/`repository`/`branch` и положительный `fileSizeBytes`, генерирует `documentId` (UUID), триммит `path` и, если путь пустой, подставляет `knowledge/docs/<documentId>.md`.
3. Gateway запрашивает presigned ссылку через gRPC `storage-service.GenerateUploadURL`, передавая `documentId`, `correlation-id`, `fileName`, размер и TTL из `uploads.signedUrlTtlSeconds`; `Authorization` (данные пользователя), `X-API-Key` и `correlation-id` прокидываются в metadata gRPC-клиента. В ответе используются `uploadUrl`, `bucket`/`objectKey`, а также `markdownBucket`/`markdownObjectKey` для конвертированной версии.
4. После получения ссылки создаётся запись через gRPC `document-service.CreateDocument` с `id`, путём (явным или дефолтным), размером, `correlation-id`, исходным `repository`, а также `uploadBucket`/`uploadObjectKey` и `markdownBucket`/`markdownObjectKey` из ответа storage-service; заголовки `Authorization`/`X-API-Key` и `correlation-id` также прокидываются в metadata. Клиент получает `documentId` и текущий статус; дальнейшие шаги выполняются на стороне document-service.
5. Мутация отвечает GraphQL-пейлоадом с сущностью `document` (включая `fileName`, `repositoryOwner`, `status`, `path`, `jobId` по приоритету `job_id`/`workflow_id`/`id` и `error`), полями `uploadUrl` и `uploadMethod = PUT`.
6. Клиент загружает файл по `uploadUrl` (HTTP PUT). После события `s3:ObjectCreated:*` MinIO отправляет webhook на `/internal/storage/uploaded`.
7. Webhook-драйвер gateway обрабатывает все записи из уведомления: декодирует `objectKey`, извлекает `documentId` из имени файла и пробует достать `correlation-id` из `x-amz-meta-correlation-id` в user metadata/response elements. Если `correlation-id` отсутствует, генерируется новый. Для каждой записи выполняется gRPC-вызов `document-service.ConfirmUpload` с bucket/objectKey/`correlation-id`. Если ни одна запись не обработана, возвращается 400, иначе 202 Accepted.
## Получение статуса
1. Запросы `knowledgeDocument` и `knowledgeDocuments` принимаются только с авторизацией (`Authorization: Bearer` или `X-API-Key`, если включён): middleware проверяет токен/ключ, добавляет/пробрасывает `x-correlation-id` и данные пользователя, а gRPC-клиенты передают заголовки в metadata downstream-сервисов.
2. Поддерживаются фильтры по статусу и репозиторию, а также пагинация (`limit`/`offset`, по умолчанию `limit = 10`, `offset = 0`).
3. Логи, метрики и трейсинг уходят в OTLP collector; заголовок `X-Correlation-ID` возвращается клиенту.
4. Ответы мапятся в GraphQL-тип `KnowledgeDocument` с `fileName`, `repository`/`repositoryOwner`, `branch`, `path`, `status`, `jobId` (из `job_id` → `workflow_id` → `id`) и `error`, после чего возвращаются клиенту; идентификатор используется downstream-сервисами для дальнейшей обработки документа.
