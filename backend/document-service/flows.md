# Бизнес-потоки

1. **Создание документа**
   - Клиент вызывает `CreateDocument` с именем файла; `id` может быть передан, при отсутствии генерируется UUID.
   - Если не заданы владелец, репозиторий, ветка или base-branch, подставляются значения из конфигурации; пустой `base_branch` дополнительно заменяется на текущую ветку. Репозиторий разрешается передать в виде `owner/repo` — владелец берётся из префикса, лишние слэши или несовпадение owner/repo приводят к ошибке.
   - `upload_bucket`/`markdown_bucket` подтягиваются из конфигурации, если не переданы. `upload_object_key` и `markdown_object_key` обязательны: сервис валидирует непустые значения и сохраняет их как есть, не создавая ключи и не вызывая `storage-service` в этом методе. Путь публикации берётся из `path`, а при отсутствии заполняется значением `knowledge/docs/<document_id>.md`, а не именем файла.
   - В PostgreSQL создаётся запись с `status=Uploaded`, `workflow_id=document_id`, флагом `create_pr`; версия `1` фиксируется в `document_versions`, в `document_status_logs` добавляется переход в `Uploaded`.

2. **Подтверждение загрузки**
   - Gateway-service вызывает `ConfirmUpload(document_id, bucket, object_key)` после успешного `UploadOriginal`/webhook-а из MinIO.
   - Сервис валидирует `document_id`, совпадение бакета и ключа с сохранёнными значениями и проверяет наличие объекта через клиент `storage-service`; без настроенного клиента метод завершится ошибкой. При успехе создаётся задача `processing_jobs` со стадией `store_original` в статусе `pending`, `ActiveJobID` документа обновляется; статус документа остаётся `Uploaded`, ошибка постановки задачи переводит его в `Failed`.
   - Периодический cron-воркер `UploadReconciler` опрашивает таблицу `documents` в статусе `Uploaded`, учитывает минимальный возраст записи и повторно вызывает `ConfirmUpload`, используя сохранённые bucket/object_key; записи без bucket/object_key пропускаются.

3. **Обработка по статусам**
   - Цепочка построена на таблице `processing_jobs`. Stage worker обрабатывает pending-задачи по стадиям, меняя статус задачи на `completed` или `failed`, а JobFollower реагирует на завершённые задачи, планируя следующую стадию или фиксируя ошибку документа.
   - `store_original` выполняется внутри stage worker: он проставляет документу статус `StoredOriginal` и закрывает задачу.
   - `JobFollower` каждую итерацию читает `completed`/`failed` задачи. После `store_original` он выбирает следующую стадию по матрице (учитываются `router.preprocess_*`, `router.table_extractor_*`, `extract_tables`, `conversion_strategy` и расширение): `pdf` с таблицами (`extract_tables=true` или `conversion_strategy=tables_only`) → `extract_tables` (если включён table-extractor), `doc`/`pdf` при `router.preprocess_enabled=true` → `preprocess_to_docx`, `docx` и остальные → `convert_to_markdown`. Завершение `preprocess_to_docx` планирует `convert_to_markdown`, завершение `extract_tables` или `convert_to_markdown` ставит `publish_to_github` с параметрами публикации, commit/pr/author из конфигурации и correlation_id. Если задача упала, JobFollower помечает документ `Failed`, используя `payload.last_error`; если сам документ уже в `Failed`, новые стадии не планируются.
   - `preprocess_to_docx` использует отдельный интервал `stage_worker.preprocess_retry_delay` для опроса статуса preprocess-service: при статусах `PENDING/PROCESSING` задача переводится в `pending` c `next_run_at=now+preprocess_retry_delay`, временные gRPC-ошибки дают экспоненциальный backoff от этого же интервала. Значение 15s из примера конфигурации совместимо с `poll_interval=2s` сервиса предобработки и избавляет от минутных пауз для маленьких файлов.
   - `extract_tables` на первом проходе вызывает `ExtractTablesFromPdf(wait=false)` и сохраняет `queue_id`/`artifacts_prefix`/`artifacts_bucket` в payload; далее опрашивает `GetTableExtractionJob` с экспоненциальным бэкофом по `stage_worker.retry_delay`. Статус `DONE` помечает документ `ConvertedToMarkdown` с `markdown_object_key=<artifacts_prefix>/tables.md`, статус `FAILED` — ошибкой задачи/документа.
   - Для `convert_to_markdown` stage worker подставляет недостающие bucket/object_key/расширение/markdown-ключ из документа (предпочитая сохранённые версии) и вызывает gRPC `ConvertDocumentToMarkdown` без ожидания результата. При наличии `preprocessed_bucket/object_key` они становятся источником для Transformer; иначе берётся оригинальный объект документа. Transformer-service возвращает `queue_id` и Markdown; если статус не готов, задача переводится в `pending` с `next_run_at` = now + retry-delay. Временные gRPC-ошибки (`Unavailable`, `DeadlineExceeded`, `Internal`, `Aborted`, `ResourceExhausted`) приводят к переотложенной задаче с экспоненциальной задержкой и счётчиком попыток (до 5), после превышения лимита документ помечается `Failed`. Когда результат готов (или документ уже конвертирован/опубликован), stage worker фиксирует версию (следующий номер, queue_id и markdown_object_key из ответа или payload) и переводит документ в `ConvertedToMarkdown`.
   - Для `publish_to_github` stage worker заполняет payload из документа (репозиторий/ветки/путь/markdown-ключ/commit и PR-данные), требуя непустые `commit_message`, `author_name` и `author_email`, добавляет `idempotency_key` при наличии markdown-ключа и вызывает `github-publisher-service`. В `job_events` сохраняются `commit_sha`, `pull_request_*`, `retry_after`, `idempotency_hit`. Временные gRPC-ошибки откладывают задачу с экспоненциальным бэкофом, остальные ошибки помечают задачу как `failed`, и JobFollower переводит документ в `Failed` (retry_after лишь фиксируется в payload). Успешный вызов переводит документ в `PublishedToGitHub` и может обновить версию, если она задана.

4. **Ручное обновление статуса**
   - Клиент вызывает `UpdateDocumentStatus`. Допустимы переходы `Uploaded → StoredOriginal → ConvertedToMarkdown → PublishedToGitHub`, повторное выставление текущего статуса, либо перевод в `Failed` (если `error_reason` не задан, используется `reason`). Восстановление после ошибки допускает переход из `Failed` в `StoredOriginal`/`ConvertedToMarkdown`/`PublishedToGitHub`.
   - Переданные `version`, `markdown_object_key` или `original_object_key` создают/обновляют запись `document_versions`, при необходимости обновляют ключи в документе. Лог статуса пишется при смене статуса, добавлении версии или переданном `reason`. После перехода в `StoredOriginal` или `ConvertedToMarkdown` сервис сам ставит задачи следующей стадии.

5. **Чтение и список**
   - `GetDocument` возвращает документ с актуальными версиями и статусом.
   - `ListDocuments` выдаёт список в порядке `created_at DESC` с пагинацией и опциональным фильтром по статусу.

6. **Фоновые помощники**
   - `UploadReconciler` периодически ищет документы в статусе `Uploaded`, проверяет возраст записи и повторно вызывает `ConfirmUpload` с сохранёнными bucket/object_key; проверка наличия оригинала происходит внутри `ConfirmUpload` через клиент storage-service.
   - `ProcessingReconciler` возвращает зависшие задачи в статусе `in_progress`, если они превысили интервал стадии плюс grace-период: задачи переводятся обратно в `pending` с ближайшим `next_run_at`, операция выполняется с ретраями и экспоненциальной задержкой.
   - Cron-воркеры опираются на `processing_jobs` и повторяют попытки согласно счётчикам `attempts` и расписанию `next_run_at`, записывая детали в `job_events`.

7. **Обработка ошибок в воркфлоу**
   - Если любой шаг (`ConfirmUpload` с невалидными ссылками, `ConvertToMarkdown`, `PublishMarkdown`) завершается ошибкой или не находит необходимые данные, stage worker или JobFollower проставляют `Failed` с текстом причины, и цепочка останавливается до ручного восстановления. Временные gRPC-ошибки (`Unavailable`, `DeadlineExceeded`, `Internal`, `Aborted`, `ResourceExhausted`) не помечают документ, а переоткладывают задачу с экспоненциальным бэкофом; после превышения лимита попыток документ получает `Failed`.
