# Сценарии использования

1. **Регистрация документа и подготовка ключей**
   - Клиент вызывает `CreateDocument`, передавая имя файла и (опционально) идентификатор, владельца, репозиторий, ветки, путь публикации и флаг `create_pr`.
   - Сервис валидирует имя и UUID (если не указан, генерируется новый), проверяет формат `owner/repo` и отсутствие конфликта с явно переданным владельцем. Пустые поля `owner`, `repository`, `branch`, `base_branch` заполняются дефолтами конфигурации (`base_branch` по умолчанию берётся из целевой ветки). Если `path` пустой, он строится как `knowledge/docs/<document_id>.md`.
   - Ключи `upload_object_key`/`markdown_object_key` обязательны и должны быть заданы клиентом; дефолты применяются только к бакетам. `workflow_id` равен `document_id`, стартовый статус — `Uploaded`, создаётся версия №1 с переданными ключами.

2. **Подтверждение загрузки и постановка на обработку**
   - После загрузки оригинала клиент вызывает `ConfirmUpload`, передавая `bucket` и `object_key`. Сервис валидирует UUID документа, сверяет бакет и ключ с сохранёнными (если они заданы), проверяет существование объекта через `storage-service.GetObject`; отсутствие сконфигурированного storage‑клиента приводит к ошибке.
   - Успешный вызов добавляет в `processing_jobs` задачу `store_original` со статусом `pending` и payload с указанным бакетом и ключом, создаёт событие `scheduled` и возвращает документ с `job_id` активной задачи. Сам статус документа не меняется.

3. **Автоматическая обработка задач StageWorker**
   - Pending-задачи берутся пачками (для `convert_to_markdown` — по одной пачке и одной задаче), переходят в `in_progress` с инкрементом `attempts`.
   - `store_original`: вызывает `MarkStoredOriginal`, работает только из фактического статуса `Uploaded` (для упавших документов статус берётся из последнего успешного лога). При наличии ключей оригинала переводит документ в `StoredOriginal`, сохраняет версию и пишет лог; отсутствие ключей даёт ошибку задачи.
   - `convert_to_markdown`: достаёт документ, дополняет payload бакетами/ключами и расширением файла, при пустом markdown-ключе берёт его из документа. Вызов `TransformerService/ConvertDocumentToMarkdown` выполняется без ожидания результата; статусы `done`/`ConvertedToMarkdown` считаются готовыми и обновляют документ до `ConvertedToMarkdown` с новой версией и `queue_id`. Промежуточные статусы возвращают задачу в `pending` с задержкой `retry_delay`. Временные gRPC-ошибки (`Unavailable`, `DeadlineExceeded`, `ResourceExhausted`, `Internal`, `Aborted`) откладывают задачу с экспоненциальным backoff; при превышении 5 попыток документ помечается `Failed`. Если документ уже в `ConvertedToMarkdown` или `PublishedToGitHub`, воркер считается idempotent и не вызывает конвертер.
   - `publish_to_github`: собирает репозиторий/ветки/путь из документа и дефолтов, наследует `create_pr`, формирует idempotency key `publish:<document_id>:<branch>:<markdown_key>` при наличии ключа. Коммит и PR‑тексты подставляются из конфигурации, но `commit_message`, `author_name` и `author_email` обязательны — их отсутствие приводит к ошибке задачи. Успех переводит документ в `PublishedToGitHub` и сохраняет `commit_sha`/PR‑данные в событиях; временные ошибки откладываются с backoff, ответы с `retry_after` откладываются, но задача остаётся `failed` до обработки `JobFollower`.

4. **JobFollower и переходы между стадиями**
   - Периодически читает завершённые/упавшие задачи (после `reschedule_after`), переносит их `next_run_at` и ставит новые стадии.
   - Для `store_original` добавляет `convert_to_markdown` с ссылками на оригинал, markdown-бакет, корреляционный ID. Для `convert_to_markdown` добавляет `publish_to_github`, подставляя репозиторий/ветки/путь, `create_pr`, commit/PR‑шаблоны и автора из конфигурации.
   - Любая задача со статусом `failed` приводит к установке документа в `Failed` с текстом из `payload.last_error`; дальнейшая автоматизация останавливается до ручного исправления.

5. **Ручное обновление статуса и резюме после сбоя**
   - `UpdateDocumentStatus` принимает желаемый статус, причину, версии и новые ключи. Допустимы переходы `Uploaded → StoredOriginal → ConvertedToMarkdown → PublishedToGitHub`, перевод в `Failed` из любого состояния и переходы из `Failed` в рабочие статусы; повторная установка того же статуса допускается. Если версия уже существует, новые ключи должны совпадать (иначе ошибка).
   - При установке `Failed` поле `error_reason` заполняется переданным текстом. Переданные ключи и версия обновляют `document_versions` и, при необходимости, сам документ; после переходов в `StoredOriginal` или `ConvertedToMarkdown` сервис автоматически ставит следующую задачу и запоминает её `job_id`, а при ошибке постановки помечает документ `Failed`.
   - Для документов в статусе `Failed` фактический этап берётся из последнего успешного лога, поэтому фоновые обработчики продолжают цепочку с места последнего удачного шага.

6. **Получение состояния**
   - `GetDocument` возвращает актуальный документ вместе с версиями и `job_id` активной задачи (если она есть).
   - `ListDocuments` отдаёт список с пагинацией и фильтром по статусу.

7. **Обработка ошибок и восстановление очередей**
   - `UploadReconciler` автоматически подтверждает старые записи в статусе `Uploaded` (после `min_uploaded_age`), если сохранены `upload_bucket` и `upload_object_key`.
   - `ProcessingReconciler` возвращает зависшие `in_progress` задачи в `pending`, если они превысили `stage_interval + grace_period`, инкрементирует `attempts`, пишет событие `recovered` и использует ретраи с backoff при ошибках репозитория.
   - Воркеры переводят задачи с ошибками в `failed`, прописывают `last_error`, после чего `JobFollower` помечает документ `Failed`. `ConfirmUpload` переводит документ в `Failed` только при ошибке постановки задачи `store_original`; ошибки проверки хранилища не меняют статус документа.
