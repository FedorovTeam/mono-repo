# Сценарии использования

1. **Регистрация документа и подготовка ключей**
   - Клиент вызывает `CreateDocument`, передавая имя файла и (опционально) идентификатор, владельца, репозиторий, ветки, путь публикации и флаг `create_pr`.
   - Сервис валидирует имя и UUID (если не указан, генерируется новый), проверяет формат `owner/repo` и отсутствие конфликта с явно переданным владельцем. Пустые поля `owner`, `repository`, `branch`, `base_branch` заполняются дефолтами конфигурации (`base_branch` по умолчанию берётся из целевой ветки). Если `path` пустой, он строится как `knowledge/docs/<document_id>.md`.
   - Ключи `upload_object_key`/`markdown_object_key` обязательны и должны быть заданы клиентом; дефолты применяются только к бакетам. `workflow_id` равен `document_id`, стартовый статус — `Uploaded`, создаётся версия №1 с переданными ключами.
   - Опциональные флаги `extract_tables` и `conversion_strategy` (например, `tables_only`) сохраняются вместе с документом и влияют на маршрутизацию после `store_original`.
   - Стратегия нормализуется в нижний регистр; `docling_with_tables` всегда включает `extract_tables`. Если стратегия подразумевает работу с таблицами, `StageRouter.DefaultExtractTables` может поднять флаг автоматически даже при явном `extract_tables=false`.

2. **Подтверждение загрузки и постановка на обработку**
   - После загрузки оригинала клиент вызывает `ConfirmUpload`, передавая `bucket` и `object_key`. Сервис валидирует UUID документа, сверяет бакет и ключ с сохранёнными (если они заданы), проверяет существование объекта через `storage-service.GetObject`; отсутствие сконфигурированного storage‑клиента приводит к ошибке.
   - Входные `extract_tables`/`conversion_strategy` могут переопределить сохранённые опции документа; при отсутствии явного флага таблицы включаются по умолчанию через `StageRouter.DefaultExtractTables`, если стратегия требует таблиц.
   - Успешный вызов добавляет в `processing_jobs` задачу `store_original` со статусом `pending` и payload с указанным бакетом и ключом, создаёт событие `scheduled` и возвращает документ с `job_id` активной задачи. Сам статус документа не меняется; если постановка задачи завершается ошибкой, документ немедленно переводится в `Failed` с текстом причины.

3. **Автоматическая обработка задач StageWorker**
   - Pending-задачи берутся пачками (для `convert_to_markdown` — по одной задаче и одному батчу). `AcquirePendingJobs` сразу переводит их в `in_progress` и увеличивает `attempts`; временные gRPC-ошибки откладывают выполнение с экспоненциальным backoff от `retry_delay`. При превышении 5 попыток на откладывании документ помечается `Failed`.
   - `store_original`: использует `MarkStoredOriginal` и фактический статус через `ResolveCurrentStatus`. При пустых ключах оригинала возвращает ошибку задачи; если документ уже не в `Uploaded`, шаг идемпотентно завершается. Успех переводит документ в `StoredOriginal`, сохраняет версию с `original_etag` и пишет лог.
   - `preprocess_to_docx`: собирает бакеты/ключи и `target_object_key` (по умолчанию `<original>.docx`), подставляет `correlation_id`. При пустых адресах источника или назначения шаг завершается ошибкой. Без `preprocess_job_id` вызывает `SubmitPreprocess`; статусы `COMPLETED/FAILED` завершают задачу, прочие возвращают `pending` с задержкой `preprocess_retry_delay` (по умолчанию равен `retry_delay`). Поллинг `GetPreprocessStatus` использует экспоненциальный backoff (до `retry_delay*16`), увеличивает `poll_attempts` и переносит задачу. Временные gRPC-ошибки откладываются с backoff и учитывают лимит попыток.
   - `extract_tables`: нормализует payload по документу и правилам роутера (artifacts bucket/prefix из `TableExtractionConfig`, `markdown_object_key`/`docling_markdown_object_key` по умолчанию совпадают с документом). При отсутствии `queue_id` отправляет `ExtractTablesFromPdf(wait=false)`, далее опрашивает `GetTableExtractionJob`. `PENDING/PROCESSING/FAILED_RETRYABLE` возвращают задачу в `pending` с backoff, временные ошибки — с экспоненциальным backoff. `DONE` либо использует сгенерированный `tables.md`, либо вызывает `MergeTables` для объединения базового Markdown и таблиц, после чего переводит документ в `ConvertedToMarkdown` (версия +1, `markdown_queue_id=table_queue_id`). `FAILED/UNSPECIFIED` фиксируют ошибку задачи.
   - `convert_to_markdown`: заполняет бакеты/ключи из документа и предусловий (preprocess-путь берётся при наличии), вычисляет расширение файла, наследует стратегию из документа либо входа, включает `extract_tables` для `tables_only`/`docling_with_tables` и при явных подсказках (table metadata/pages или markdown вида `tables.md`). Для уже конвертированных/опубликованных документов RPC не вызывается. Промежуточные статусы возвращают задачу в `pending` с `retry_delay`, временные ошибки откладываются с backoff (до 5 попыток, затем документ падает). Готовый ответ сохраняет очередь/метаданные; если `StageRouter.ShouldExtractTablesAfterConvert` требует таблицы (флаг в документе, стратегия, найденные таблицы или хинт для PDF с `force_table_extraction`), задача завершается без `MarkConverted` — публикация таблиц поставит `JobFollower`. В остальных случаях `MarkConverted` переводит документ в `ConvertedToMarkdown`, фиксируя исходный объект и `queue_id` в версии.
   - `publish_to_github`: собирает репозиторий/ветки/путь из документа и шаблоны коммита/PR из конфигурации, `create_pr` наследуется из документа. `commit_message`, `author_name` и `author_email` обязательны, idempotency key формируется при наличии `markdown_object_key`. Если документ уже опубликован, RPC пропускается. Временные gRPC-ошибки откладывают задачу с backoff; любые ошибки (включая ответы с `retry_after`) оставляют задачу `failed` до обработки `JobFollower`, успешный вызов переводит документ в `PublishedToGitHub`.

4. **JobFollower и переходы между стадиями**
   - Обрабатывает завершённые/упавшие задачи (после `reschedule_after`), переносит их `next_run_at` и ставит новые стадии, если документ не в `Failed`.
   - После `store_original` вызывает `StageRouter.NextStageAfterStore`: при стратегии `docling_with_tables` идёт сразу на `convert_to_markdown`; при `extract_tables=true`/`tables_only` и разрешённом расширении — на `extract_tables`; при разрешённом препроцессинге (глобальном или per-repo) и подходящих расширениях — на `preprocess_to_docx`; иначе на `convert_to_markdown`. Для `preprocess_to_docx` подтягивает `original_etag` из версии или payload и ставит задачу с корреляцией из документа.
   - После `preprocess_to_docx` формирует `convert_to_markdown` с путями/расширением из результата препроцессинга и тем же correlation_id.
   - После `convert_to_markdown` оценивает `StageRouter.ShouldExtractTablesAfterConvert`: учитывается явный флаг, стратегия (`tables_only`/`docling_with_tables`), количество таблиц из payload, страницы и markdown-хинты, а также принудительный режим для PDF. При необходимости ставится `extract_tables` с включённым `extract_tables`; иначе создаётся задача `publish_to_github` с бакетами/ключами, путём, ветками и шаблонами коммита/PR/автора из конфигурации.
   - После `extract_tables` планируется `publish_to_github`, используя итоговые markdown-бакет и ключ из документа.
   - Любая задача со статусом `failed` помечает документ `Failed` (причина строится из `payload.last_error`, если она есть) и помечает саму задачу как обработанную; документы в статусе `Failed` не получают новые стадии.

5. **Ручное обновление статуса и резюме после сбоя**
   - `UpdateDocumentStatus` принимает желаемый статус, причину, версии и новые ключи. Допустимы переходы `Uploaded → StoredOriginal → ConvertedToMarkdown → PublishedToGitHub`, перевод в `Failed` из любого состояния и переходы из `Failed` в рабочие статусы; повторная установка того же статуса допускается. Если версия уже существует, новые ключи должны совпадать (иначе ошибка).
   - При установке `Failed` поле `error_reason` заполняется переданным текстом. Переданные ключи и версия обновляют `document_versions` и, при необходимости, сам документ; после переходов в `StoredOriginal` или `ConvertedToMarkdown` сервис автоматически ставит следующую задачу по тем же правилам роутера (preprocess/extract_tables/convert/publish) и запоминает её `job_id`, а при ошибке постановки помечает документ `Failed`.
   - Для документов в статусе `Failed` фактический этап берётся из последнего успешного лога, поэтому фоновые обработчики продолжают цепочку с места последнего удачного шага.

6. **Получение состояния**
   - `GetDocument` возвращает актуальный документ вместе с версиями и `job_id` активной задачи (если она есть).
   - `ListDocuments` отдаёт список с пагинацией и фильтром по статусу.

7. **Обработка ошибок и восстановление очередей**
   - `UploadReconciler` автоматически подтверждает старые записи в статусе `Uploaded` (после `min_uploaded_age`), если сохранены `upload_bucket` и `upload_object_key`.
   - `ProcessingReconciler` возвращает зависшие `in_progress` задачи в `pending`, если они превысили `stage_interval + grace_period`, инкрементирует `attempts`, пишет событие `recovered` и использует ретраи с backoff при ошибках репозитория.
   - Воркеры записывают `last_error`, на временных gRPC-ошибках откладывают выполнение с экспоненциальным backoff; превышение лимита попыток приводит к принудительному `Failed`. Ошибки публикации (включая ответы с `retry_after`) оставляют задачу в `failed`, и `JobFollower` помечает документ `Failed`. `ConfirmUpload` переводит документ в `Failed` только при ошибке постановки задачи `store_original`; ошибки проверки хранилища не меняют статус документа.
