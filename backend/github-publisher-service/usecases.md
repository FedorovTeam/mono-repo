# Use cases

## Публикация Markdown из запроса
- **Актор:** workflow после конвертации или сервис, формирующий готовый Markdown.
- **Шаги:**
  1. Передать `path` в `PublishMarkdown` (обязательный параметр).
  2. При необходимости указать `owner`/`repository` и `branch`; если не заданы, используются значения из конфигурации (`github.owner`, `github.repository`, `github.default_branch`).
     - `repository` может содержать `owner/repo`, в этом случае параметр `owner` заполняется автоматически; комбинация `owner`+`owner/repo` считается ошибкой.
  3. Передать `commit_message` по желанию. Если он пустой, сервис сформирует его сам: `Update <path>` либо `Update markdown content`.
  4. Отправить тело `content` с Markdown или перейти к сценарию загрузки из хранилища.
  5. По желанию передать `author_name`/`author_email` для переопределения автора коммита (по умолчанию берутся из конфигурации).
  6. Прикрепить `correlation_id` в поле запроса или заголовке gRPC метаданных; имя заголовка берётся из конфигурации `github.correlation_header` (по умолчанию `X-Correlation-ID`).
  7. По желанию добавить `idempotency_key`: при повторном успешном вызове с тем же ключом вернётся кэшированный результат и флаг `idempotency_hit=true` без новой публикации.
  8. Получить SHA успешного коммита в ответе.
  9. Если содержимое файла не меняется, сервис возвращает SHA существующей версии без создания нового коммита.
  10. При ошибках возвращаются статус (`SUCCESS`/`TEMPORARY_FAILURE`/`PERMANENT_FAILURE`) и код ошибки; при временных ошибках заполняется `retry_after` с учётом переданных `attempt` и `retry_policy` (или значений по умолчанию из конфигурации).
  11. Если коммит выполнен, но создание PR не удалось, в ответе остаётся `commit_sha` и заполненные поля ошибки.

## Публикация Markdown из MinIO
- **Актор:** workflow, который уже сохранил Markdown в хранилище.
- **Шаги:**
  1. Не заполнять `content` и передать `bucket` и `object_key` в `PublishMarkdown`.
  2. Сервис загрузит Markdown через сконфигурированный клиент MinIO; при отсутствии клиента или параметров вернёт ошибку `FailedPrecondition/InvalidArgument`.
  3. Загрузка поддерживает автоопределение кодировки и конвертацию в UTF‑8, в противном случае возвращается ошибка `InvalidArgument`.
  4. Далее выполняются шаги коммита как в сценарии выше (ветка, автор, correlation-id, получение SHA).

## Создание Pull Request после коммита
- **Актор:** workflow публикации или оператор поддержки.
- **Шаги:**
  1. В запросе `PublishMarkdown` указать `create_pr=true` и ветку `branch` с изменениями.
  2. При необходимости задать `base_branch`; если не указана, используется `github.default_branch` из конфигурации.
  3. Передать `pr_title` и `pr_body` для описания изменений.
  4. Получить номер и URL созданного Pull Request из ответа.

## Обновление без PR
- **Актор:** фоновые задачи синхронизации.
- **Шаги:**
  1. Отправить `PublishMarkdown` без `create_pr` для прямого коммита в `branch` (по умолчанию `github.default_branch`).
  2. Использовать `author_name`/`author_email` для маркировки техпроцессов.
