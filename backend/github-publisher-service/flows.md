# Flows

## Публикация Markdown
1. Gateway/worker вызывает gRPC `PublishMarkdown` с путём файла, `idempotency_key`, параметрами веток (`branch`/`base_branch`), параметрами ретраев (`attempt` + `retry_policy`) и данными для PR/коммита.
2. Сервис выбирает `correlation-id`: в приоритете поле запроса `correlation_id`, иначе берётся значение из входящих метаданных по заголовку из конфигурации (`X-Correlation-ID` по умолчанию).
3. Разрешение репозитория: если `repository` передан в формате `owner/repo`, он раскладывается на поля, конфликты с явным `owner` вызывают `INVALID_ARGUMENT`. Пустые `owner`/`repository` заполняются значениями из конфигурации.
4. Контент:
   - Если `content` задан, используется он.
   - Если `content` пустой, обязателен конфигурированный загрузчик и параметры `bucket` + `object_key`; Markdown скачивается из MinIO через `LoadMarkdown`, после чего приводится к UTF-8 (BOM/UTF-16/автоопределение кодировки).
5. Перед публикацией проверяется кэш идемпотентности: повторный успешный запрос с тем же `idempotency_key` вернёт закэшированный `commit_sha`/`pull_request_*` и проставит `idempotency_hit=true` без походов в GitHub (кэш сохраняется только для успешных публикаций).
6. `commit_message` при пустом значении подставляется автоматически (`Update <path>`). Параметры веток также получают значения по умолчанию из конфигурации, если не заданы.
7. GitHub клиент делает GET `/repos/{owner}/{repo}/contents/{path}?ref={branch}`:
   - если файла нет, переходит к созданию;
   - если файл существует и его контент совпадает, публикация пропускается, возвращается актуальный SHA;
   - если файл существует и отличается, его SHA кладётся в тело PUT-запроса для обновления (заголовок `If-Match` не используется).
   После этого коммит выполняется PUT `/repos/{owner}/{repo}/contents/{path}` с Base64-контентом и автором коммита (значения берутся из запроса или из конфигурации).
8. При `create_pr=true` создаётся Pull Request POST `/repos/{owner}/{repo}/pulls` из ветки `branch` в `base_branch` (по умолчанию `default_branch`). Ошибки PR возвращаются вместе с `commit_sha`, чтобы потребитель мог зафиксировать факт коммита отдельно от PR.
9. Попытка публикации повторяется до `max_attempts` по стратегии экспоненциального бэкоффа (с учётом переданного `attempt`). Временные ошибки возвращают `status=TEMPORARY_FAILURE` и `retry_after` с рекомендуемой задержкой.
10. В ответе возвращаются `status`, `error_code/message`, `commit_sha`, `pull_request_number/url` (если PR создан), `retry_after` и флаг `idempotency_hit`. В логах каждого шага фигурирует `correlation-id`.

## Ошибки и валидация
- `INVALID_ARGUMENT`: пустой `path`; `bucket`/`object_key` при пустом `content`; невалидная кодировка загруженного файла; конфликтующие значения `owner` и `repository` в формате `owner/repo`.
- `FAILED_PRECONDITION`: не сконфигурирован storage при отсутствии `content`; ошибки загрузки из MinIO.
- Ошибки GitHub классифицируются: 401/403 → `PERMISSION`, 404 → `NOT_FOUND`, 409 → `CONFLICT`, 429/5xx и сетевые/таймауты → временные с `retry_after`, остальное → `UNKNOWN`.
- При всех ошибках в логи добавляется `correlation-id`, указанный в запросе или метаданных.
