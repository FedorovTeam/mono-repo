# Flows

## Конвертация DOCX → Markdown через очередь
1. Gateway или cron-воркер `document-service` вызывает gRPC метод `ConvertDocumentToMarkdown` с `document_id`, `original_bucket`, `original_object_key` и опционально `markdown_bucket`/`markdown_object_key`; флаг `wait_for_result=true` заставляет сервис дождаться финального статуса очереди и вернуть готовый `markdown_object_key`/`queue_id`. Повторный вызов с тем же `document_id` возвращает уже существующую задачу в статусах, отличных от `failed`, без создания дублей.
2. gRPC слой валидирует обязательные поля, определяет расширение файла из `filename_extension` или `original_object_key`, проверяет поддержку формата и лимит очереди (`service.queue_limit`) через `CountByStatus` для статусов `pending`/`processing`/`waiting_docling`. При переполнении возвращается `ResourceExhausted`. В отсутствие `markdown_bucket`/`markdown_object_key` подставляются значения по умолчанию из конфига и `BuildMarkdownKey`.
3. В PostgreSQL добавляется запись в `transformations_queue` со статусом `pending` (ключевые поля: `document_id`, `original_bucket/key`, `markdown_bucket/key`, `filename_extension`, `retry_count`, `correlation_id`, `docling_job_id`, `docling_poll_count`, `next_poll_at`). Клиент получает `queue_id`, статус `pending` и путь для Markdown или финальный статус при `wait_for_result=true`. Correlation ID фиксируется для трассировки и восстановления после перезапуска. Если включён `wait_for_result`, gRPC-слой опрашивает статус через `WaitForResult`, учитывая `docling.status_*` backoff и `next_poll_at`; по исчерпании лимита попыток возвращается `DeadlineExceeded`.
4. При старте сразу выполняется цикл обслуживания очереди: он снимает метрики, активирует задачи `waiting_docling` с наступившим `next_poll_at` (или помечает их как `failed`, если превышен `docling.max_job_lifetime`) и восстанавливает/завершает зависшие `processing`, если они превысили `service.processing_timeout` с учётом `scheduler.max_processing_retries` и `docling.status_max_attempts`.
5. Фоновый воркер по таймеру выбирает пачку задач (`scheduler.batch_size`) через `FOR UPDATE SKIP LOCKED`, ставит им статус `processing`, увеличивает `retry_count` для свежих попыток и сбрасывает `next_poll_at`. В выборку попадают и ранее отложенные `waiting_docling`, которые переводились в `pending` на шаге обслуживания.
6. Если у задачи нет `docling_job_id`, воркер скачивает исходник из MinIO с коротким таймаутом, собирает имя файла и отправляет документ в Docling на `/v1/convert/file/async` с заголовками `X-Correlation-Id`, `X-Docling-Source-Filename`, `X-Docling-Endpoint` и `X-Api-Key` (при наличии). После успешного `submit` сохраняется `docling_job_id`, `docling_poll_count=0`, рассчитывается `next_poll_at` и задача переводится в `waiting_docling` без повторной загрузки файла.
7. Если `docling_job_id` уже есть, воркер опрашивает `/v1/status/poll/{job_id}`. При промежуточных статусах выставляется новый `next_poll_at` по экспоненциальному backoff и задача остаётся в `waiting_docling`. При успехе воркер запрашивает `/v1/result/{job_id}`, определяет медиатип (по умолчанию `text/markdown; charset=utf-8`), загружает результат в MinIO и ставит статус `done`. При ошибках фиксируется `failed` с описанием причины; превышение лимитов по опросам или таймаутам также попадает в ошибку.
8. Отдельный фоновый цикл каждые `scheduler.maintenance_interval` снимает метрики очереди, возвращает в работу задачи `waiting_docling` с наступившим `next_poll_at`, помечает просроченные по `docling.max_job_lifetime` как `failed`, восстанавливает либо завершает зависшие `processing` (использует `service.processing_timeout`, `scheduler.max_processing_retries`, `docling.status_max_attempts`), возвращает в `pending` записи `failed` старше `scheduler.failed_retry_delay` пока `retry_count < scheduler.max_failed_retries` (иначе дописывает в ошибку причину исчерпания ретраев) и удаляет завершённые (`done`/`failed`) старше `scheduler.cleanup_retention`.

## Синхронная конвертация без очереди
1. gRPC метод `ConvertDocxToMarkdown` принимает либо `docx_content`, либо `docx_url` (оба поля одновременно запрещены). Если передан URL, сервис скачивает файл через встроенный HTTP‑клиент с валидацией кода ответа.
2. Имя файла берётся из `filename` или из пути URL; тип контента определяется по расширению, неподдерживаемые форматы блокируются ещё до обращения к Docling.
3. Сервис отправляет документ напрямую в Docling через `POST /v1/convert/file/async` с прокидыванием `X-Correlation-Id`/`X-Docling-Endpoint`/`X-Docling-Source-Filename` и ключа API. Результат опрашивается в цикле `CheckStatus` → `result/{job_id}` с backoff `docling.status_*` и без сохранения в очередь/БД.
4. При успехе gRPC ответ возвращает сгенерированный Markdown, медиатип и charset. При истечении лимита попыток или ошибках Docling клиент получает `DeadlineExceeded`/`Internal`.

## SLA и таймауты
- `service.processing_timeout` — максимальное время нахождения задачи в статусе `processing`; по превышению задача восстанавливается в `pending` (или переводится в `failed`, если превышен лимит ретраев или опросов Docling).
- `service.io_timeout` — ограничение на быстрые операции (скачивание/загрузка, submit в Docling), не влияющее на ожидание внешнего сервиса.
- `scheduler.maintenance_interval` — период сервисного цикла, который выполняет восстановление/очистку очереди.
- `scheduler.cleanup_retention` — TTL, после которого завершённые задачи (`done`/`failed`) удаляются из очереди.
- `scheduler.failed_retry_delay` / `scheduler.max_failed_retries` — интервал до повторного запуска `failed` задач и ограничение на количество их запусков; при превышении лимита статус остаётся `failed`.
- `docling.status_initial_interval` / `docling.status_backoff_factor` / `docling.status_max_interval` — параметры экспоненциального backoff для опроса статуса Docling (рост до 30–60 минут при ожидании 1–2 часов).
- `docling.status_max_attempts` — ограничение на общее число запросов статуса (0 — без ограничений).
- `docling.max_job_lifetime` — максимальное время нахождения задачи Docling в ожидании; по превышению задача помечается как `failed`.

## Управление конфигурацией
1. При старте `cmd/server` читает `config.yaml` (или путь из `CONFIG_PATH`).
2. Подключения к Docling, MinIO и PostgreSQL берут параметры из конфига, без `.env`.
3. Любые изменения конфига требуют перезапуска сервера; формат задокументирован в README.
