# Flows

## Конвертация DOCX → Markdown через очередь
Перед запуском фоновых циклов сервис восстанавливает возможные «зависшие» задания: при старте все записи в статусе `processing` переводятся обратно в `pending`, чтобы ни одна задача не потерялась после рестарта воркера.
1. Gateway или воркер `document-service` вызывает gRPC метод `ConvertDocumentToMarkdown` с `document_id`, `original_bucket`, `original_object_key` и опционально `markdown_bucket`/`markdown_object_key`, `source_bucket`/`source_object_key` **или** `source_url` (взаимоисключающие), `filename_extension`, `correlation_id`. Если `correlation_id` не передан, сервер генерирует его сам. При `wait_for_result=true` метод дополнительно ждёт финальный статус очереди и возвращает `markdown_bucket/object_key` вместе с `queue_id`. Повторный вызов с тем же `document_id` и статусом не `failed` возвращает существующую задачу без дубликатов.
2. gRPC слой проверяет обязательные поля, запрет одновременного `source_url` и `source_bucket`/`source_object_key`, а также необходимость передачи парных `source_*` полей. Расширение определяется из `filename_extension` или `original_object_key`, нормализуется и валидируется через `ResolveContentTypeByExtension`; неподдерживаемые форматы приводят к `InvalidArgument`. При пустом `markdown_bucket` берётся значение из конфига, при пустом ключе — `BuildMarkdownKey`. Лимит очереди (`service.queue_limit`) контролируется через `CountByStatus` (`pending`/`processing`/`waiting_docling`) с ошибкой `ResourceExhausted` при переполнении.
3. В `transformations_queue` создаётся запись со статусом `pending`, где сохраняются ссылки на исходник (original и optional source), целевой Markdown bucket/key, нормализованное расширение, `correlation_id`, `docling_poll_count=0`, пустые `docling_task_id/job_id`, `next_poll_at=NULL`. Клиент получает `queue_id`, статус `pending` и путь для Markdown либо финальный статус при `wait_for_result=true`. Метод `WaitForResult` использует статусный backoff из конфига, учитывает `next_poll_at`, если он отложен на будущее, и возвращает `DeadlineExceeded`, когда лимит попыток/ожиданий исчерпан.
4. При запуске поднимаются два фоновых цикла: `QueueWorker` и `MaintenanceRunner`. `QueueWorker` постоянно пытается взять задачи пачками и обрабатывать их, `MaintenanceRunner` сразу снимает снимок очереди и далее по таймеру считает метрики, помечает `waiting_docling`, просроченные по `docling.max_job_lifetime`, как `failed`, восстанавливает `processing` старше `service.processing_timeout` (переводит в `pending` либо фиксирует `failed`, если превышены `scheduler.max_processing_retries` или лимит опросов Docling), повторно запускает `failed`, которые старше `scheduler.failed_retry_delay` пока `retry_count < scheduler.max_failed_retries`, и чистит завершённые (`done`/`failed`) старше `scheduler.cleanup_retention`.
5. `QueueWorker` сначала пытается взять `waiting_docling` с `next_poll_at <= now()` и переводит их в `processing`. Если в очереди вообще есть записи `waiting_docling` (даже с будущим `next_poll_at`), `pending` задачи не выдаются. `pending` разбираются только когда нет ни одной задачи в статусе `waiting_docling`; выборка упорядочена по `created_at` и пропускает записи с `next_poll_at` в будущем.
6. Если у задачи нет `docling_task_id/job_id`, `ConversionExecutor` готовит параметры: задаёт bucket/key по умолчанию, определяет расширение и content type, вычисляет реальное имя файла, выбирает режим `source_async` (если включён в конфиге и не передан `source_url`, либо если явно переданы `source_bucket/object_key`). В режиме `source_async` Docling получает ссылку на исходник в хранилище (поля `source_bucket/object_key`), иначе сервис скачивает файл по URL или из MinIO с быстрыми таймаутами. Отправка в Docling обёрнута advisory-локом `pg_try_advisory_lock`: при занятом локе задача возвращается в `pending` с `next_poll_at=now()+submit_lock_delay`. Реальная отправка идёт на `/v1/convert/file/async` или `/v1/convert/source/async`; внутри конвертера есть до 5 быстрых ретраев для временных ошибок. Если Docling временно недоступен и ретраи исчерпаны, задача остаётся без идентификаторов, переводится в `waiting_docling` с `next_poll_at` по `docling.status_*` и будет переотправлена позже. Успешный `submit` сохраняет `docling_task_id/job_id`, сбрасывает счётчик опросов и ставит `next_poll_at` через backoff.
7. Задачи с заполненными Docling ID обрабатываются через `DoclingPoller`: каждое обращение к `/v1/status/poll/{id}` увеличивает `docling_poll_count` и сохраняет идентификаторы. Если статус ещё «в работе», задача остаётся `waiting_docling` с новым `next_poll_at`. Повторяющиеся ошибки статуса или достижение лимита опросов (`docling.status_max_attempts`) приводят к `RequeueDoclingWaiting`: статус `pending`, очищенные Docling ID/счётчики, рост `retry_count` и отложенный `next_poll_at` на `scheduler.docling_requeue_delay`. При успехе запрашивается `/v1/result/{id}` и результат сохраняется в MinIO в целевой `markdown_object_key`; `MarkDone` фиксирует финальные ссылки, `MarkFailed` — ошибку. Markdown загружается после единственного успешного ответа Docling без промежуточных стадий.
8. `MaintenanceRunner` периодически повторяет проверки: снимает метрики очереди, помечает просроченные `waiting_docling` как `failed`, восстанавливает или завершает зависшие `processing`, перезапускает старые `failed` в пределах лимита и чистит старые `done`/`failed`. Возврат `waiting_docling` в работу выполняет обычный цикл воркера, а не maintenance.

## Синхронная конвертация без очереди
1. gRPC метод `ConvertDocxToMarkdown` требует передать либо `docx_content`, либо `docx_url` (оба сразу запрещены); при отсутствии контента метод скачивает документ по URL встроенным HTTP‑клиентом и отклоняет неуспешные HTTP‑коды или пустой ответ.
2. Имя файла вычисляется из `filename` или хвоста `docx_url`; расширение валидируется так же, как в очереди. Корреляционный ID генерируется при необходимости и прокидывается в Docling.
3. Документ отправляется напрямую в Docling (`/v1/convert/file/async` или `/v1/convert/source/async` согласно конфигу), затем `CheckStatus` опрашивает результат с backoff `docling.status_*` без помещения задачи в очередь или БД.
4. При успехе gRPC возвращает Markdown, медиатип и charset. Если лимит попыток ожидания исчерпан или Docling вернул ошибку, клиент получает `DeadlineExceeded`/`Internal`.

## SLA и таймауты
- `service.processing_timeout` — используется `MaintenanceRunner` для поиска зависших `processing`; такие задачи переводятся в `pending` или `failed` с учётом `scheduler.max_processing_retries` и `docling.status_max_attempts`.
- `service.io_timeout` — быстрые операции: скачивание/загрузка объектов и отправка в Docling выполняются в отдельных контекстах с этим таймаутом.
- `scheduler.maintenance_interval` — период обслуживания очереди (метрики, восстановление/очистка).
- `scheduler.cleanup_retention` — TTL для удаления `done`/`failed` записей.
- `scheduler.failed_retry_delay` / `scheduler.max_failed_retries` — окно и лимит на повторный запуск `failed` задач; при превышении лимита запись остаётся `failed` с пояснением.
- Отправка в Docling: до 5 мгновенных ретраев с backoff 0.5s → 5s; после исчерпания временных ошибок задача переводится в `waiting_docling` с `next_poll_at` по `docling.status_*`.
- `docling.status_initial_interval` / `docling.status_backoff_factor` / `docling.status_max_interval` — интервалы экспоненциального backoff для ожидания статуса Docling (используются и в `WaitForResult`, и в `DoclingPoller`).
- `scheduler.docling_requeue_delay` / `scheduler.docling_max_restarts` — пауза и ограничение рестартов при потере задания Docling; при срабатывании лимита задача переводится в `pending` с отложенным `next_poll_at`.
- `docling.status_max_attempts` — предел опросов статуса до переочереди/ошибки (0 — без ограничений).
- `docling.max_job_lifetime` — задачи, зависшие в `waiting_docling` дольше лимита, помечаются `failed`.

## Управление конфигурацией
1. При старте `cmd/server` читает `config.yaml` (или путь из `CONFIG_PATH`).
2. Подключения к Docling, MinIO и PostgreSQL берут параметры из конфига, без `.env`.
3. Любые изменения конфига требуют перезапуска сервера; формат задокументирован в README.
